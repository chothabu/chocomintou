# チョコミン党 設計 v1.1

v1.0 設計からの変更点は「商品と店舗を完全に別データとして管理し、その間をユーザーの目撃情報でつなぐ」こと。
この 1 点がアプリの中核概念になるため、影響範囲（データモデル / マップ / 外部 API の位置づけ / 実装順）をここに集約する。
v1.0 で決めた画面構成・レビュー仕様・図鑑・v1.0 でやらないことの一覧は据え置き。

---

## 1. コンセプト

**全国のチョコミントを収集していく「図鑑 + レーダー」**

- 図鑑 = 何が存在するか（Product）
- レーダー = 今どこで見つかるか（Sighting → Store）

レビューアプリではない。レビューは図鑑の付加情報という位置づけにする。

---

## 2. 中核となる 3 層モデル

```
Product（商品マスタ）           「○○チョコミントアイス」
  ・店舗情報を一切持たない
  ・全国で一意。メーカー / 発売日 / 販売状況を持つ
        │
        │  Sighting（目撃イベント：ユーザーが生成する唯一の事実）
        │  「2026-08-19 13:42 に この商品を この店で見た」
        ↓
Store（店舗マスタ）             「ファミリーマート渋谷○○店」
  ・商品情報を一切持たない
  ・位置と名前とチェーン名だけを持つ
```

重要な原則：

1. **Product と Store は直接リレーションを持たない。** 両者をつなぐのは Sighting だけ。
2. **Sighting は追記のみのイベントログ。** 消さない（取り消しは論理削除）。
3. **StoreProduct は Sighting の集計キャッシュであり、事実ではない。** いつでも Sighting から再計算できる導出データとして扱う。

この分離により、店舗マスタの調達手段（ぐるなび / OSM / 自前登録）を後から差し替えても、商品データと目撃データは無傷で残る。

店舗との関係を持たない。「販売場所」はメーカー公式告知に基づく**テキスト情報**にとどめ、実在店舗とは結合しない。

| id | uuid | |
| name | text | |
| manufacturer | text | |
| description | text | |
| category | text | アイス / お菓子 / ケーキ / パフェ / ドリンク / パン / その他 |
| image_url | text | 運営管理のみ |
| price | int | null 可（不明時は非表示） |

### sightings（中核）

| column | type | 備考 |
|---|---|---|
| id | uuid | |
| product_id | uuid | |

| user_id | uuid | |

制約：同一 (user_id, product_id, store_id) の投稿は **1 日 1 件**（UNIQUE インデックスで担保）。連投で目撃数を水増しさせない。

### store_products（集計キャッシュ）

| column | type |
|---|---|
| store_id / product_id | uuid（複合 UNIQUE） |
| first_seen_at / last_seen_at | timestamptz |
| sighting_count | int |
| distinct_user_count | int |

Sighting の INSERT / 論理削除をトリガに upsert。全件再構築するバッチも用意する（整合性が壊れても復旧できるようにする）。

### product_channels（新規）

商品がどのチェーンで売られる**予定か**を構造化して持つ。
主用途は**検索フィルタの「チェーン」絞り込み**（セブン / ファミマ / ローソン / ミニストップ）で、これは Phase 1 の検索機能に必要。
副次的に、マップの「候補ピン」の材料にもなる（§5）。

| column | type | 備考 |
|---|---|---|
| product_id | uuid | |
| chain_name | text | stores.chain_name と同じ語彙 |
| area | text | 全国 / 地域名。null は全国 |

Store とは `chain_name` でゆるく結合するだけ。「この店に在庫がある」という主張ではない。

### 変更なしのテーブル

`users` / `reviews` / `review_reports` / `tasted_products` / `wishlists` / `news_articles` / `product_submissions` / `blocked_users` は v1.0 のまま。

## 4. 目撃の鮮度（freshness）

`store_products.last_seen_at` から算出する。判定は v1.0 の定義を踏襲。

| 経過 | 表示 |
|---|---|
| 〜24h | 🟢 今日見つかっています |
| 1〜7日 | 🟡 最近見つかっています |
| 8〜30日 | ⚪ 過去に見つかっています |
| 30日超 | 非表示 |

「在庫あり」とは絶対に書かない。すべて「見つかりました」表現に統一する。
これは正確さの問題であると同時に、在庫 API を持たないことへの誠実な表現でもある。

## 5. マップの表示ロジック

**v1.0 では目撃実績のあるピンだけを表示する。** 初期データは運営が自分で足で集めて投入する（§9）。

| ピン | 意味 | 根拠 | 時期 |
|---|---|---|---|
| **濃いピン（実績）** | ここで見つかった | 30 日以内の Sighting がある | v1.0 |
| 薄いピン（可能性） | 置いてあるかも | product_channels のチェーンに該当する店舗 | v1.1 以降 |

薄いピン（候補表示）は見送る。理由は、実際には無い店にピンが立つと「行ったのに無かった」体験を生み、
このアプリが唯一持っている資産である**目撃情報の信頼性そのものを毀損する**ため。
地図が空であること自体は、嘘の情報が載っているより害が小さい。

ただし `product_channels` テーブルは検索フィルタのために Phase 1 から作る（§3）ので、
候補ピンを後から足すのはクエリと UI だけの追加で済む。判断は運用データを見てから行う。

デフォルト条件：`sale_status != ended` かつ `last_seen_at > now() - 30 days`
下部トグル「販売中のみ」で `sale_status = on_sale` に絞る。

## 6. 店舗マスタの調達方針（変更あり）

v1.0 の「ぐるなび起点」から方針を変更する。理由は、ぐるなびは飲食店の情報源であり、チョコミントの主戦場である**コンビニ・スーパーをカバーできない**ため。

採用する方針：**目撃報告フローで必要になった店舗だけを、その場で Store に登録する（オンデマンド生成）**。

```
「この商品を見つけた」
   ↓ 現在地から周辺店舗を検索（MKLocalSearch）
   ↓ 候補一覧から店舗を選ぶ
   ↓ その店舗が stores に未登録なら、この時点で INSERT
   ↓ sightings に INSERT
```

利点：事前に全国の店舗マスタを用意する必要がない。実際に使われた店舗だけが自然に溜まる。

**MapKit（MKLocalSearch）の結果を自前 DB に保存する**（2026-08-20 決定）。
店舗マスタの調達元は MapKit で確定とし、代替検討は打ち切る。

- iOS 18 以降は MapKit が返す安定した POI 識別子を `external_store_id` に使う。
  取れない場合（iOS 17）は店名と座標から組み立てた値を使う。
- 2 つの採番が混在しても、`report_sighting` が「同名かつ 50m 以内」でも名寄せするため
  同じ店舗が重複登録されることはない。
- 乗り換えの余地は残す。`external_source` に `mapkit` を記録してあるので、
  将来 OpenStreetMap / Overpass（ODbL、帰属表示が必要）に切り替える場合も既存データと区別できる。

**ぐるなび API は v1.0 では使わない**（決定）。飲食店に特化した情報源であり、主戦場のコンビニ・スーパーを
カバーできないため、契約確認のコストに見合わない。カフェ・飲食店のメニュー（パフェ・ドリンク）を
本格的に扱う段階で再検討する。

いずれの経路でも `external_source` / `external_store_id` を必ず記録し、後からソースを差し替え・重複統合できるようにする。

## 7. 商品詳細画面「どこで買えるか」（新規セクション）

商品詳細に、公式情報と目撃情報を**明確に分けて**並べる。

```
どこで買える？

公式情報
  全国のファミリーマート

近くで見つかっています
  🟢 セブンイレブン渋谷○○店     750m   今日 13:42
  🟡 ファミリーマート神南店      1.2km  3日前

                          マップで見る >
```

「公式情報 = メーカーの告知」「見つかっています = ユーザーの報告」という出所の違いをラベルで示す。

## 8. API（変更部分）

```
POST /sightings                      目撃報告（中核）
DELETE /sightings/{id}               自分の報告の取り消し

GET  /stores/nearby                  lat, lng, radius, product_id?, fresh_days=30
                                     → 目撃実績のある店舗（濃いピン）
GET  /map/candidates                 lat, lng, radius, product_id
                                     → chain 一致の候補店舗（薄いピン）

GET  /products/{id}/sightings/nearby lat, lng → 商品詳細の「近くで見つかっています」
GET  /stores/{id}/products           店舗詳細の「この店舗で見つかった商品」
```

その他のエンドポイントは v1.0 のまま。iPhone から外部サービスへ直接アクセスしない原則も変更なし。

## 9. 実装順（確定）

目撃情報をレビューより先に作る。レビューは商品数が少ない初期には集まらないが、目撃情報は
**1 人が 1 個見つけるだけで即座に他人の役に立つ**ため、初期のコンテンツ密度を作れるのはこちら。

| Phase | 内容 |
|---|---|
| 1 | Product DB → 商品一覧 → 商品詳細 → 検索・絞り込み |
| 2 | Sign in with Apple → 食べた / 食べたい |
| **3** | **Store → 目撃報告 → MapKit → 店舗詳細** |
| 4 | レビュー投稿 / 表示 / 通報・ブロック |
| 5 | ニュース収集バッチ → ニュース画面 |
| 6 | 図鑑 → プロフィール → ランキング → 通知 |

### 初期データ投入（シード）

コンテンツのコールドスタートは、運営が自分で足で集めたデータで埋める。専用の投入ツールは作らない。

```
Phase 1 完了時点   管理画面で商品を登録（商品マスタだけ先に埋める）
Phase 3 完了時点   現地でアプリの目撃報告フローをそのまま使って投入
```

店舗はオンデマンド生成（§6）なので、店舗マスタを事前に用意する必要はない。現地で報告した分だけ溜まる。
アプリの投稿フローを運営自身が使うので、リリース前に本番導線を通しで検証できるという副次効果もある。

シード分の目撃は `sightings.is_official = true` を立てて区別する。用途は次の 2 つ：

- 表示上「運営が確認」と出せる
- 集計上の扱いを変えられる（例：一般ユーザーの報告が 1 件も無い店舗を、30 日の鮮度ルールで消すか残すか）

判断は運用しながら決めればよく、フラグさえ持っておけば後から選べる。

## 10. バックエンドの構成（§47 の具体化）

v1.0 設計の「iPhone → Backend API → PostgreSQL」という原則は維持するが、Supabase を採用するなら
自前のバックエンド API を書く必要はない。PostgREST + RLS がそのバックエンドの役割を果たす。

| 経路 | 用途 | 鍵 |
|---|---|---|
| iPhone → Supabase（supabase-swift 直接） | 商品 / 店舗 / 目撃 / レビュー / 図鑑 | anon key。RLS で保護 |
| iPhone → Edge Functions | 外部 API を叩く処理 | 秘密鍵はサーバ側のみ |
| バッチ（cron / Edge Functions） | ニュース記事の収集、楽天の商品候補収集 | service_role |
| Web 管理画面 → Supabase | 商品承認 / 通報対応 / ユーザー停止 | service_role |

§47 の主眼は「API キーを iOS アプリに埋め込まない」ことであり、この構成はそれを満たす。
anon key は公開前提の識別子で、実際のアクセス制御は RLS が行う。
**service_role key はアプリに絶対に入れない**（サーバ側のみ）。

外部 API を iPhone から直接叩かない原則は変更なし。

### ニュースの収集元（2026-08-20 変更）

v1.0 設計の「Google News RSS から収集する」は**取りやめる**。
フィード自身の `copyright` に次の記載があり、この使い方が明示的に禁じられているため。

> This XML feed is made available solely for the purpose of rendering Google News results within a
> personal feed reader for **personal, non-commercial use. Any other use of the feed is expressly prohibited.**

代わりに、**収集元を運営が管理画面から登録する方式**にする。

- `news_sources` テーブルに名前とフィード URL を登録し、有効にしたものだけを巡回する
- RSS 2.0 / RDF / Atom のいずれでも読める
- 収集元をコードに書かないので、利用条件が変わったフィードはコードを触らず止められる
- どのフィードを使うかは、その利用条件を確認したうえで運営が判断する

保存するのはタイトル・リンク・媒体名・日時だけで、本文は保存しない（v1.0 の方針どおり）。

### 店舗情報をどこから取るか（2026-08-23 調査）

「チョコミントを売っている実店舗」を返す API は**存在しない**。調べた結果は次のとおり。

| 情報源 | 得られるもの | 採否 |
|---|---|---|
| 楽天市場 API | 通販の取扱店（店名・商品ページ） | **採用**。実店舗ではないが検証済みの事実 |
| ホットペッパー グルメ API | 飲食店の位置・キーワード検索 | **不採用**。実測でヒット 0 件（下記） |
| Google Places API | 店舗・口コミ（5 件まで） | **不採用**。実測で精度・件数とも足りず、保存も不可（下記） |
| OpenStreetMap / Overpass | コンビニ・スーパーの位置とチェーン名 | 保存可（ODbL・要帰属表示）。ただし商品情報は無い |
| MapKit（MKLocalSearch） | 周辺店舗の位置 | 目撃報告フローで採用済み（§6） |

つまりコンビニ・スーパーについては「店の位置」と「商品」が別々にしか取れず、
**両者を結ぶ情報が世の中に無い**。だからこのアプリは目撃情報でつなぐ（§2）。

#### ホットペッパー グルメ API の扱い

当初は「取得データの DB 保存が規約違反」と判断したが、条文を読み直したところ誤りだった。
[利用規約](https://cdn.p.recruit.co.jp/terms/rws-t-1001/index.html)は次のように定めている。

- 禁止されているのは「**第三者の**データベースへの複製保存」と、許諾外の用途でのコンパイル
- 保持そのものは想定されており、「個別に定める規定がない場合は**キャッシュの更新頻度を
  24 時間以内**と定めます」とある
- 画面に「リクルートより提供」の旨を表示する必要がある
- 「本 API の利用もしくは提供から収入を得ること」は事前の書面承諾が必要

つまり **24 時間以内に更新するキャッシュとしてなら使える**。規約は障害ではなかった。

そこで採否を実用性で判断するため、実際のヒット件数を測った（`collectors/src/hotpepper-probe.ts`）。
結果は次のとおりで、**採用しない**。

| キーワード | 全国のヒット件数 |
|---|---|
| チョコミント | **0** |
| ミントチョコ | **0** |
| ミント | 30 |
| チョコ | 47 |
| アイス | 155 |
| デザート | 739 |

部分一致は機能している（「ミント」「チョコ」は単体ならヒットする）。それでも
「チョコミント」が全国 0 件なのは、`keyword` の対象が店名・住所・駅名・ジャンル・
店舗のフリーワードであって、**メニュー 1 品ごとの情報ではない**ため。
店の紹介文に「チョコミント」と書く飲食店が事実上存在しない。

したがって、規約をクリアしても取れるデータが無い。飲食店のみで
コンビニ・スーパーをカバーしないという制約以前の問題だった。

プローブは残してある。将来ヒットするようになったか確かめたいときに再実行できる。

**口コミやメニューから引けないかも確認したが、これも不可。**

- API のレスポンスに**口コミもメニュー品目も含まれていない**。口コミ用の API も無い
- キーワード検索が拾わないフリーテキスト欄（`catch` / `shop_detail_memo` /
  `budget_memo` / `other_memo`）を直接調べるため、渋谷 3km 圏の 300 店を走査した結果：

  | 語 | 該当店舗数（300 店中） |
  |---|---|
  | チョコミント | 0 |
  | ミント / チョコ | 0 |
  | パフェ / アイス / デザート | 各 1 |
  | ケーキ | 7 |
  | スイーツ | 11 |

  ヒットするのはジャンルを表す語だけで、**メニューの品目はそもそも入っていない**。

残る手段はホットペッパーのサイトから口コミを直接取得することだが、それは食べログと
同じく規約違反になる（§ 下記「検索して転載する案」）。

#### 検索してグルメサイトから転載する案（2026-08-23 却下）

`"チョコミント" site:tabelog.com` のように検索し、店舗ページからメニュー名・価格を
取得して自前 DB に入れる案を検討したが、**採らない**。

検索してリードを見つけるところまでは正当だが、店舗ページの内容を取り出して保存する
段階が各サイトの規約に反する。食べログの[利用規約](https://tabelog.com/help/rules/)は明確で、

> 第9条(1)① 食べログの提供する情報を当社の事前の同意なく、複写、若しくはその他の方法により
> 再生、複製、送付、譲渡、頒布、配布、転売、又は**これらの目的で使用するために保管すること**

「保管」まで名指しで禁じている。第6条(1)①で営利目的のアクセスも禁止。
ぐるなび・ホットペッパーも同種の条項を持つ。

規約を別にしても、他社のデータを複製したデータベースはこのアプリの資産にならない。
食べログを見れば済む情報を並べ直しても、ここにしかない価値は生まれない。

**代わりに取れる形**: 検索は「どこを見に行くか」の手掛かりに使い、運営が実際に確認して
自分で登録する。DB に入るのは他社のデータではなく、自分で確かめた事実になる。

#### Google の口コミから取れないか（2026-08-23 実測）

Places API の Text Search は口コミ本文も検索対象にすると説明されているため、
「チョコミントがおいしい」と書かれた店を拾えないかを試した。**使えなかった。**

実測（Text Search / 日本・渋谷周辺）:

| クエリ | 返ってきた店 |
|---|---|
| チョコミント | キャットミント（店名に MINT）、リンツ、メリーチョコレート … |
| チョコミントパフェ | チョコバナナ専門店、夜パフェ専門店 … |
| チョコミントアイス 販売 | ゴディバ、セブン-イレブン渋谷マークシティ店 … |

**店名の断片（チョコ / ミント / パフェ / アイス）に反応しているだけ**で、
チョコミントを出す店を選んでいない。上位 8 店の口コミ 40 件を実際に取得して調べたところ、
**チョコミントに言及した口コミは 0 件**だった。

仮に精度が良くても、次の 2 点で成立しない。

1. **Place Details が返す口コミは 1 店あたり 5 件まで**。口コミを横断検索する API は無いので、
   「チョコミントに言及した口コミを探す」という使い方が構造的にできない。
2. [利用規約](https://developers.google.com/maps/documentation/places/web-service/policies)により
   **Places のコンテンツは保存できない**（place ID のみ例外）。口コミは改変せず表示し、
   投稿者名・アイコン・Google マップへのリンクを併記する義務もある。
   店舗を自前 DB に持つ本アプリの構成とは噛み合わない。

加えて Text Search は呼び出しごとに課金される。取れる情報の質に対して割に合わない。

商品詳細の「どこで買える？」は 3 段に分ける。出所の違いが読み手に分かることを優先する。

| 段 | 内容 | 出所 |
|---|---|---|
| 公式情報 | 「全国のファミリーマート」など | メーカーの告知 |
| 通販で買える | 取扱店名 + 商品ページ | 楽天の出品（実在を確認済み） |
| 近くで見つかっています | 店舗 + 最終目撃 | ユーザーの報告 |

### マップの「周辺のお店」（2026-08-23 追加）

目撃情報がゼロの地域で地図が真っ白になる問題への対処。
MKLocalSearch の周辺店舗を、**目撃ピンとは明確に区別した小さな白丸**で出す。

- 「ここで売っている」とは言わない。タップすると「目撃情報はまだありません」と表示する
- 目撃ピン（色つき）とは形・大きさ・色をすべて変える
- 近距離（半径 2km 以下）でのみ表示し、8 件までに絞る（密集地で団子になるため）

§5 で見送った「候補ピン」とは別物。候補ピンは「このチェーンなら置いてあるはず」という
**推測を在庫情報として出す**ものだったが、これは在庫について何も主張せず、報告先を示すだけ。

### 商品候補の収集

楽天市場の商品検索 API から候補を集める（v1.0 設計 §26 のとおり）。集めた結果は
`product_submissions` に `source = 'rakuten'` として積み、運営が承認したものだけが `products` になる。
ユーザーからの商品報告と同じテーブル・同じ承認フローを通す。

楽天ウェブサービスのアプリ ID が必要で、未設定なら収集はスキップされる。

**チョコミン党**（2026-08-21 決定）
